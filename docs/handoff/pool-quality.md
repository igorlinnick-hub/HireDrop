# pool-quality — описание → балл → ранжирование → тейлоринг

Обновлено: 2026-09-15 · ветка: main

Одна цепочка: **чем наполняем пул → видит ли скорер описание → как ранжируем → за что
платим.** Все три звена ломались по одной причине: комментарий описывал намерение, а
читался как описание системы.

## Замер пула 09-15 (1307 строк)

`indeed 425 (100% без описания, не скорились) · greenhouse 326 · ashby 204 · lever 144 ·
workday 121 ❌ · linkedin 25 ❌ (avg 7.72!) · remoteok 61`
Баллы по 719 вакансиям с описанием: `1→322 · 2→307 · 3→30 · 6→16 · 7→2 · 8+→0`.

## Закрыто

  тайтл и оценивала ВЫСОКО. 24 из 26 прошедших гейт тейлоринга были безописательные
  LinkedIn. A/B живьём: `6,8,6 → 5,5,5`.
- **#193** — харвест шлёт сниппет карточки (Indeed+ZR), `/jobs/ingest` скорит от
  `MIN_SCORABLE_DESC=120`. Обещанного в докстринге «description-bearing pass» не
  существовало: `_backfill_thin_ats_scores` покрывал только greenhouse/lever.
- **#194** — гейт тейлоринга снят (рудимент: проходили 2 из 719; `fit_score` нигде не
  сохраняется, но у `resume/url/best` один вызывающий = «мы подаём»). Цена замерена:
  $0.0070/вызов, заявка $0.0129 → $0.0199. Workday убран из сбора в
  `WORKDAY_BOARDS_PARKED`, сторож — `tests/test_watchlist_platforms.py`.

## 🔁 Точки возврата — прогнать ПОСЛЕ первого живого прогона

```sql
select count(*) as indeed_24h,
       count(*) filter (where coalesce(description,'') <> '') as with_desc,
       count(score) as scored,
       round(avg(length(description)) filter (where coalesce(description,'')<>'')) as desc_len
from jobs where platform='indeed' and created_at > now() - interval '24 hours';
select count(tailored_resume) from jobs where created_at > now() - interval '24 hours';
```

- `with_desc = 0` → расширение не синкнуто/не перезагружено (грабли №1–2 в `CLAUDE.md`), **не** сервер.
- `desc_len < 80` → переехал селектор карточки, чинить `extractCardInfo`, а не скоринг.
- сниппеты в среднем ВЫШЕ полных описаний → #192 повторился, поднимать порог.

## Инвентарь: потолок был не в вотчлисте, а в капе (замер 09-15)

`discover_ats(..., cap=160)` применял кап к СОБРАННОМУ, до дедупа вызывающего против пула.
Ранжирование детерминированное (zero-touch → квота по платформам) → каждый прогон тратил
160 слотов на те же строки, просачивалась только текучка. 378/мес — это не предложение
бордов, это скорость просачивания.

Живой замер (213 бордов, ключи «social media / marketing / project manager»): доступно
**560** уникальных вакансий (4865 без фильтра по ключам), возвращалось 160 → **71% уже
скачанного выбрасывалось каждый прогон**. Ни одна доска не упёрлась в `limit=50`, ни одна
не отрезана дедлайном 35 с (сам sweep — 14,5 с).

Новых строк за 5 прогонов: было `160·80·64·35·45` → стало `160·160·160·80·0`
(ноль = предложение честно кончилось).

Фикс: `discover_ats(..., exclude=jobs_db.all_links(user_id))`. Кап ограничивает НОВЫЕ
строки, стоимость прогона та же (160 × **$0,0019/строку** = ~$0,30), пул выходит на
реальное предложение за 4 прогона.

**Цена строки пула замерена впервые:** Haiku, 863 вх / 204 вых = $0,0019.
`scripts/measure_ai_cost.py` патчит только `ai_cover_letter` и `ai_fit_judge` — скорер
пула, единственная статья, растущая ВМЕСТЕ с инвентарём, в замер не входил.

## Открыто

- **560 строк стоячего предложения против капа 900 заявок/мес.** Дальше пул растёт
  скоростью появления вакансий на 213 бордах — её и надо мерить, а не размер вотчлиста.
  «Прогон вернул 0» теперь = вотчлист исчерпан, сигнал измеримый.
- **Indeed зажат `iafilter=1`** (только Indeed Apply) в `goBackToIndeedJobList` + ~24
  страницы на прогон. Тот же класс ограничения, что был у капа, на другой оси; не замерено.
- **Lever:** 144 строки / 15 компаний, капча per-company, `CAPTCHA_OVERRIDES` не пишет
  никто. Выучить 15 компаний или выкинуть из подачи. Солвер отвергнут — бьёт в
  единственный реальный бан-риск (снятие с CWS), а релизы мы сами отдаём на ревью.
