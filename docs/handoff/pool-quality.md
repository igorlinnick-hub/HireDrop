# pool-quality — описание → балл → ранжирование → тейлоринг

Обновлено: 2026-09-15 · ветка: `fix/indeed-scoring`

Одна цепочка, четыре звена: **чем наполняем пул → видит ли скорер описание → как
ранжируем → на каком основании тратим дорогой тейлоринг.** Каждое звено ломалось
отдельно и чинилось отдельно, поэтому здесь они вместе.

## W1 — Indeed должен скориться (В РАБОТЕ)

**Почему не скорится.** Это осознанное решение, записанное в докстринге `/jobs/ingest`:
сервер **никогда** не скрейпит Indeed (compliant-by-design), карточки приходят из браузера
юзера, а скоринг по одному тайтлу — шум. `score` остаётся `null`, и строка сортируется
после всех.

**Почему это тупик.** Докстринг обещает «until a description-bearing pass rescores them»,
но такого прохода для Indeed **не существует**: `_backfill_thin_ats_scores` фильтрует
`platform in ("greenhouse", "lever")`. 425 строк (треть пула, VERIFIED-платформа) остаются
с `null` навсегда.

**Почему НЕ чиним «обогащением на подаче».** Описание появляется, когда расширение открывает
страницу вакансии — то есть в момент, когда мы уже подаём. Балл, приехавший тогда, ранжировать
уже нечего. Ранжирование нужно РАНЬШЕ: в колоде, которую юзер свайпает.

**Решение: брать сниппет с карточки поиска.** Он уже есть в DOM выдачи (`job-snippet`),
лишних заходов на страницы не требует (а значит и ban-риска не добавляет), и это настоящее
описание, пусть тонкое.

| шаг | где | статус |
|---|---|---|
| 1. `/jobs/ingest` скорит строки, пришедшие С описанием; title-only остаются `null` | сервер | ✅ 09-15 |
| 2. `extractCardInfo` забирает сниппет, harvest его шлёт (Indeed **и** ZR) | `content.js` | ✅ 09-15 |
| 3. синк расширения + OFF/ON + живой прогон | **Игорь** | ⬜ **ждём** |
| 4. проверить, что новые строки приходят со `score` и описанием | проверка | ⬜ |
| 5. пересмотреть распределение баллов на сниппетах | решение | ⬜ |

Порог тонкости — `MIN_SCORABLE_DESC = 120` в `app/routers/jobs.py`. Ответ `/jobs/ingest`
теперь отдаёт `scored` и `unscored_title_only`: «saved 15, scored 0» читается как
регрессия извлечения сниппета, а не как тихий день.

### 🔁 Точки возврата (команды, а не «посмотреть глазами»)

```sql
-- после шага 3: приехали ли описания и баллы у свежих Indeed-строк
select count(*) as indeed_24h,
       count(*) filter (where coalesce(description,'') <> '') as with_desc,
       count(score) as scored,
       round(avg(score) filter (where score is not null), 2) as avg_score,
       round(avg(length(description)) filter (where coalesce(description,'')<>'')) as avg_desc_len
from jobs
where platform = 'indeed' and created_at > now() - interval '24 hours';
```

**Ожидаем:** `with_desc ≈ indeed_24h`, `scored ≈ indeed_24h`.
**Если `with_desc = 0`** — расширение не синкнуто или не перезагружено (грабля №1 и №2
в `jobflow/CLAUDE.md`), а не баг сервера. Проверять `scripts/sync-ext.sh` ПЕРЕД тем,
как лезть в код.
**Если `avg_desc_len < 80`** — сниппет пустой, селектор карточки переехал; чинить
`extractCardInfo`, а не скоринг.

```sql
-- шаг 5: как сниппеты ложатся на шкалу против полных описаний
select case when length(description) < 300 then 'сниппет' else 'полное' end as kind,
       count(*), round(avg(score), 2) as avg_score, count(*) filter (where score >= 7) as ge7
from jobs where score is not null and coalesce(description,'') <> '' group by 1;
```

**Если сниппеты в среднем ВЫШЕ полных описаний** — повторяется баг #192 в новой форме
(меньше информации = выше балл), и порог тонкости надо поднимать, а не радоваться.

## W2 — гейт тейлоринга: `jobs.score >= 7` → «мы подаём» (ЖДЁТ РЕШЕНИЯ ИГОРЯ)

**Гейт ни на чём не основан.** История: сначала просто захардкожено 7; коммит `ceab921`
растянул в 6/7/8 под apply_mode — дословно *«was hardcoded 7»*. Само число взято из
словесной рубрики в промпте скорера («8-10=strong, 5-7=worth considering»). Долю реальных
вакансий, которые его проходят, никто не мерил: **2 из 719**.

**Гейт — рудимент.** Когда тейлоринг был жадным (на этапе Find Jobs), `jobs.score` был
единственным сигналом. Коммит `391558b` перенёс тейлоринг на момент подачи, **а гейт не
перенёс**. На момент подачи у нас уже есть вердикт судьи.

**Чем заменить.** `fit_score` **нигде не сохраняется** — живёт только в памяти расширения
и в строчках лога (проверено: `grep fit_score` по `app/` даёт только литерал 0 в фоллбэке).
Поэтому серверный гейт его прочитать не может. Но замена проще: у
`GET /profile/resume/url/best` **ровно один реальный вызывающий** —
`content.js:3667 → uploadResume()`, то есть заполнение формы перед отправкой. Достижение
этого эндпоинта САМО ПО СЕБЕ и означает «мы подаём». Гейт по баллу там лишний.

**Цена, замерено 09-15:** `tailor_resume` = **$0.0070** за вызов (in 1027 / out 261),
а не $0.0219, как я оценивал. Если тейлоринг начнёт срабатывать на каждой заявке:

| | $/заявка | маржа на капе 900/мес после 30% комиссии |
|---|---|---|
| сейчас (тейлоринг ~никогда) | $0.0129 | +$14.26 |
| после (тейлоринг всегда) | **$0.0199** (+54%) | **+$7.96** |

На наблюдаемом потреблении (31 заявка/мес) разница $0.40 → $0.62 в месяц.

✅ **Проверено 09-15, тревога была ложной.** Те 261 токен — артефакт МОЕГО тестового ввода:
синтетическое резюме было склеено из повторяющегося блока, и модель его схлопнула. На
реалистичном резюме (921 символ) тейлоринг отдаёт **1467 символов** — полный документ, все
секции на месте, работодатели / даты / должности / образование не тронуты, метрика «21%»
сохранена. Качество выхода запуску фичи не мешает.

Единственное, за чем стоит приглядывать: модель подняла заголовок с «Project Manager» на
«Senior Project Manager». Это не выдумка (последняя должность действительно Senior), но
если начнёт повышать там, где оснований нет, — это первый признак.

## W3 — Workday собирается, но подать туда нельзя (ЖДЁТ РЕШЕНИЯ ИГОРЯ)

**Ответ на «подключена или нет»: подключена для СБОРА, не подключена для ПОДАЧИ.**

- `data/ats_watchlist.py` → `SEED_WATCHLIST` = 222 борда, из них **9 workday**
  (nvidia, adobe, salesforce, mastercard, hp, paypal, target, workday…).
- `ats_boards._FETCHERS["workday"] = fetch_workday` — сервер их тянет.
- Расширение туда не ходит: `background.js:693` → `ATS_PLATFORMS = ["greenhouse", "lever", "ashby"]`.
- `STATUS_MATRIX.json`: workday DEFERRED, открыть только когда core-5 VERIFIED **и Игорь даст
  аккаунт Workday** для многошаговой подачи.
- Код это признаёт прямым текстом: *«scrapeable coverage but the extension never walks them
  (workday ∉ ATS_PLATFORMS)»*.

Итог: **121 строка (9% пула) — вакансии, которые невозможно подать.** Плюс LinkedIn 25 —
вместе 146 строк, и до #192 именно они занимали верх сортировки.

Варианты: убрать 9 workday-бордов из watchlist до подключения · оставить и фильтровать при
показе (#189) · оставить как есть и признать это осознанным.
