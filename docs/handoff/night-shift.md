# night-shift — серверный исполнитель ATS-подач (пока юзер спит)

Обновлено: 2026-09-23. Лейн запущен по решению Игоря 09-21..23. Тест — на его аккаунте
(a0775013). Резюме и письма признаны готовыми, остальное — механика.

## Зачем (и почему браузер не годится)

Расширение подаёт только пока машина бодрствует. Замер 09-23: «ночной» браузерный прогон
нашёл 3 discovered-вакансии против 505 в пуле, закончился за секунды; закрытая крышка =
сон железа = стоп (keep-awake систему держит, крышку — нет, это hardware). Overnight-подача
возможна ТОЛЬКО с сервера, идущего по всему пулу. Компромисс «ночным исполнителем будет сам
Mac юзера» — отвергнут Игорем 09-23: крышку закрывают, и это не лечится софтом.

## Что выяснено (разведка, read-only)

- **Greenhouse: reCAPTCHA Enterprise в SCORE-режиме** — `grecaptcha.enterprise.execute(key,
  {action:"apply_to_job"})`, `recaptcha.net/recaptcha/enterprise.js`. **Челленджа нет и
  «решать» нечего**: токен выдаётся всегда, но несёт оценку 0.1–0.9. Оценку ЗАРАБАТЫВАЮТ
  репутацией IP + fingerprint + поведением. Низкий score → GH молча принимает форму и
  роняет заявку в спам — **отказа мы не увидим**. Это главный риск лейна.
- **Payload сабмита** — `job_application` + csrf + fingerprint + `jobApplicationRequestToken`
  + recaptcha-токен ⇒ чистый HTTP-POST хрупок и палевен. **Основной путь — Playwright**.
- **Ashby**: два reCAPTCHA site-key на живой странице, GraphQL-интроспекция закрыта.
  Считаем аналогом Greenhouse; второй в очереди.
- **Lever — не берём** (интерактивная капча per-company). **Indeed/ZR серверу не даём**
  (403 + бан-сигнатура, решено ранее).
- **Солвер капч НЕ запрещён для этого лейна.** Прошлый отказ (память pool-quality) был
  из-за политики Chrome Web Store — она про расширение. Сервер вне CWS, так что
  CapSolver/2captcha с Enterprise-токенами (score 0.7–0.9) — легальный **fallback**,
  если собственная репутация не вытянет. Но это план Б: платим за каждый токен и зависим
  от чужой фермы.

## Вердикт совета (llm-council, 09-23) — принят

Это **другой класс риска**, не тот же, что расширение: расширение = N независимых рисков
(у каждого юзера свой IP/fingerprint), сервер = один коррелированный (общий egress, одна
сигнатура) — одна детекция травит всех. Отсюда инварианты ниже. Расхождение совета
(«может, вообще не надо, keep-awake хватит») закрыто решением Игоря: крышка.

## Инварианты (нарушение = стоп лейна)

1. **Один резидентный IP = один юзер**, sticky. Общий пул травит всех разом.
   Railway/датацентр-IP — **не транспорт для подачи** (почти гарантированный низкий score).
2. **Не-headless** (`headless=new` палится), реальный persistent-профиль с историей.
3. **Честность записи**: заявка пишется в БД ТОЛЬКО по положительному доказательству
   отправки. Нет доказательства — нет записи. (09-23 нарушено, см. P1.)
4. **Kill-switch**: первый challenge/reject/аномалия — пауза всей ночной смены, не одного юзера.
5. **Версионный лог**: в каждой заявке — какой транспорт/конфиг её подал. Иначе инцидент
   не разобрать.
6. **Кап общий с расширением** (30/день), власть — бэкенд. Ночь не добавляет объёма, она
   добавляет ВРЕМЯ.
7. Ночная смена — только auto-юзерам (решение 09-21), tap не трогаем.

### P1 — ЧЕСТНОСТЬ ИСПОЛНИТЕЛЯ 🔴 СЕЙЧАС
Первый live-прогон (09-23, Zocdoc) записал заявку как поданную, **не отправив её**: три
обязательных `select` остались пустыми («This field is required»), а детектор успеха принял
слово «submitted» на странице за подтверждение. Запись откатана вручную. Это делает тихую
деградацию неотличимой от работы — чинить раньше любой архитектуры.
- [ ] `select`/radio/checkbox-вопросы заполняются (сейчас `select` пропускается, radio/checkbox — `continue`).
- [ ] Детектор успеха = **положительное доказательство**: URL confirmation ИЛИ исчезновение
      формы ИЛИ явный текст подтверждения. Плюс **проверка на ошибки валидации** до клика и после.
- [ ] Не-отправленная заявка = hand-back с причиной, НИКАКОЙ записи в applications.
- [ ] Скриншот «после» смотреть глазами на каждом прогоне, пока не устаканится.

### P2 — КОНТУР ВЕРИФИКАЦИИ ДОСТАВКИ (переписан 09-23 по разведке — старый план был на ложной посылке)

⚠️ **Отменено: «свой борд = мишень, владелец видит score».** Разведка (5 агентов + скептики,
09-23) проверила живьём: **Greenhouse и Ashby раздают ОДИН глобальный site-key на всех
клиентов** — GH `6Lfmcbcp…` идентичен на боардах anthropic/discord/vercel, Ashby `6LeFb_YU…`
идентичен на ramp/linear/deel. Ключ принадлежит вендору, assessment живёт в ЕГО Google-проекте,
арендатору видна только «spam sensitivity». **Свой борд score не покажет никогда.** Заодно:
GH без self-serve (sandbox только Pro-тариф, партнёрский — нужен общий клиент), Ashby от
$400/мес. Не покупать, не выпрашивать — сэкономлено ~$6.5k/год и недели переписки.

⚠️ **Отменено: свой калибровочный reCAPTCHA-ключ.** Идея «поднять свой Enterprise score-key и
мерить конфиги» разбита скептиком цитатой Google: для v3 «создавайте отдельный ключ для тестовых
окружений, **score может быть неточным — reCAPTCHA полагается на реальный трафик вашего сайта**»,
а новый ключ отдаёт `LOW_CONFIDENCE_SCORE`. Чужой score нашим ключом не предсказывается.

✅ **Чем меряем вместо этого — ответом самого Greenhouse.** GH **не дропает молча**: при низком
score он просит **код из почты** (док GH «Invisible reCAPTCHA»: *«a user may be asked to submit a
code from their email to verify their identity»*; сабмит отвечает **428**, на странице появляются
поля `#security-input-0..7` и `security_code_recipient`). То есть **провал видимый и считаемый
прямо из прогона** — ни борда, ни стенда, ни солвера для замера не нужно.
- [ ] Инструментовать ответ сабмита через `page.on("response")` на XHR подачи. **Четыре** исхода,
      не три: `200` подано · `428` captcha-failed (нужен код) · ошибка валидации формы · прочее.
      Валидационная ошибка проверяется ПЕРВОЙ (иначе наш же баг P1 маскируется под капчу).
- [ ] Счётчик `428` на 100 подач = наша метрика репутации. Она же — гейт для трат на транспорт.
- [ ] Квитанция доставки без борда: Ashby по умолчанию шлёт кандидату письмо-подтверждение;
      почта юзера — дешёвый receipt (не строить ради этого Gmail-OAuth — он убит решением).
- [ ] **Гейт P2→P3: доля 428 измерена на ≥50 реальных подачах с жилого IP** (база сравнения).

## Грабли (уже оплаченные)

- `fit_score` нигде не хранится; `jobs.score` 0–10 ≠ fit 0–100. Серверный фильтр зовёт `assess_fit`.
- Пул-ссылки Ashby в БД с задвоенным `/application/application` → 404; базовый URL живой.
- GH-вакансии протухают быстрее, чем пул перепроверяется: 461 «new» строк, свежих за 2 дня — 5.
- Резюме брать только через `best_signed_url`/`resume_text_for` (диал `default_resume`), не оригинал.
- Замер вести по ТОМУ user_id, под которым идёт прогон, и от `started_at` (грабли 09-22).
- Файл исполнителя уже переписывали параллельные сессии — перед правкой `git pull`.
- **Ashby пишется по СХЕМЕ, не по селекторам** (разведка 09-23): `POST
  jobs.ashbyhq.com/api/non-user-graphql?op=ApiJobPosting` с `{organizationHostedJobsPageName,
  jobPostingId}` отдаёт без авторизации `applicationForm.sections[].fieldEntries[]` — `field.path`,
  тип (`StringField/EmailField/PhoneField/LongTextField/BooleanField/FileField/ValueSelectField/
  MultiValueSelectField/…`), `isRequired`, `selectableValues[{label,value}]`, плюс `recaptchaAction`
  и `surveyForms` (EEO). Значит fit-гейт и генерацию ответов можно гонять ДО открытия браузера.
  На странице поля адресуются контейнером `.ashby-application-form-field-entry[data-field-path="…"]`.
  Интроспекция GraphQL закрыта — операцию звать по имени. Ashby в середине миграции на Enterprise
  (флаги `MigrateGoogleRecaptchaToEnterprise`, `UseGoogleRecaptchaUniversalKey`) — на части оргов
  ещё классический v3.
