# campaign-runtime

Обновлено: 2026-09-20 · ветка: `breadth-keyword-walk` · ext: **1.8.7** (в проде 1.8.6, в CWS 1.8.3)

## Состояние

Цикл: скрейп → фильтры → fit-гейт → walk по платформам → подача. Окно автоматизации **видимое**
(политика CWS), превью через CDP. Auto и Tap делят один движок; капы слоёные — серверная правда
`app/db/subscriptions.py`, клиентский ban-гейт с SAFE-дефолтом 20, на 429 стоп (#95).

**Порядок стадий (с 09-13, #189)**: Indeed → ZipRecruiter → ATS-пул, пул ВСЕГДА последний.
Живёт в двух чистых функциях `background.js`: `pickAtsOpener` (на чём прогон открывается) и
`pickNextStage` (куда передаёт ход). Пул достижим только через `PLATFORM_EXHAUSTED` — тем же
путём, что любая доска, поэтому «конец прогона» существует в одном месте. Переключаться можно
только на ВЫБРАННЫЕ юзером платформы. Фикстуры: `tests/platform-order.test.js` (14, включая
проверку, что цепочка передач завершается и не зацикливается).

**Очередь ATS = текущий поиск, не архив**: `GET /jobs/ats-queue` режет пул общим
`on_search_filter()` — тем же, что колода тапа. Отката к нефильтрованному пулу при ошибке нет.

Паузы-с-передачей-человеку — по одной схеме (строка в окне + лента + `DETECTION_TRIPPED` +
авто-возврат + стоп через 2 ч): капча (#72), логин-стена, стена согласия (#182). Капча в
pool-режиме СКИПАЕТ пик, стена согласия ПАУЗИТ и там (аккаунт-широкая); Accept не жмём.

Терминальная строка прогона несёт `metadata.outcome` (`completed` / `stopped_by_user`).
Отсутствие outcome = прогон оборвался (закрытый ноут, убитое окно) — дашборд читает именно
отсутствие, не текст строки.

## Последний заход (09-20) — обход переведён в ШИРИНУ, курсор ролей починен на сервере

Ветка `breadth-keyword-walk`, ext **1.8.7**. Закрыта задача №1 из плана 09-19 плюс её
настоящая третья часть, которая оказалась не там, где её искали.

**Что поменялось в обходе** (`content.js`, блок «keyword rotation»):
- **1 страница на ключевик → ротация по всему списку → второй круг.** Бюджет страниц тот
  же (`pagesPerKeyword` = max(4, 24/n)), поменялся ПОРЯДОК: теперь это число КРУГОВ, а
  круг = номер страницы. Круг 0 — страница 1 у КАЖДОЙ фразы (при `sort=date` это самая
  свежая голова), круг 1 — страница 2 у каждой, и так далее. Один ключевик по-прежнему
  идёт вглубь на 24 страницы — для него ничего не изменилось.
- **Под-кап `MAX_PER_PLATFORM / n` на ключевик** (`keywordSubCap`). Одной ротации на
  границе страниц НЕ ХВАТАЕТ: на одной выдаче Easy Apply-карточек бывает больше, чем весь
  дневной кап, поэтому фраза №1 всё равно уносила все 15. Пре-сабмитный гейт в
  `phase2_indeed` / `phase2_ziprecruiter` при исчерпании доли уводит прогон на список, а
  тот ротирует. Леджер — `keywordCounts[platform][kwIndex]`, тот же дневной ключ, что у
  `platformCounts`; пул/ATS-обход в него НЕ пишет и под-капом не управляется (иначе
  очередь увело бы в поиск по борду — зеркало провала 09-13).
- **Фраза без результатов уходит в отставку на прогон** (`kwDone`). Старый ZR-страж ждал
  двух пустых страниц ПОДРЯД — при обходе в ширину эти две страницы теперь принадлежат
  РАЗНЫМ фразам, и он отправил бы в отставку не ту.
- Фикстура: `chrome-extension/tests/keyword-breadth.test.js` (11 проверок — ширина, круг
  как номер страницы, срез капа, пропуск отставных/исчерпанных, завершаемость, одиночный
  ключевик, неприкосновенность пула). Запуск: `node chrome-extension/tests/keyword-breadth.test.js`.

**⚠️ «kwIndex сбрасывается в 0 на каждом старте» — диагноз был верным по симптому и
неверным по месту.** Сбрасывать `kwIndex` в расширении ПРАВИЛЬНО: с 09-11 (#187) список
ролей ротирует СЕРВЕР — `modules/keyword_rotation.rotate()` в `/campaign/start`, курсор
`kw_cursor` в `campaign_states.filters`, а дашборд арминг делает ответом сервера, не своим
локальным списком (`QuickActions.tsx:408`). Расширение всегда берёт индекс 0 того списка,
который ему выдали. Второй курсор в `chrome.storage` пошёл бы вперёд независимо от
серверного, и они бы разъехались.

Настоящая поломка была в том, что курсор **не доживал до следующего прогона**:
`campaign_db.stop()` затирал `filters` в `{}` — а прогон ВСЕГДА кончается стопом. Значит
`prev_cursor` на каждом старте читался как 0, и ротация, отгруженная 09-11, никогда не
происходила. Это и есть механизм замера «39 из 39 на keyword #1». Теперь `stop()` сохраняет
`kw_cursor` и ничего больше (остальное в `filters` — про закончившийся прогон).
Тесты: `tests/test_keyword_rotation.py` (+2).

**Проверка на живых данных** (после нескольких прогонов у юзера с 4+ ключевиками): подачи
в `applications` распределены по всем ключам, а не сидят на первом — запрос из «Последнего
захода (09-19)» ниже воспроизводит замер.

**НЕ сделано в этой ветке, ждёт живого прогона**: ни один реальный прогон на 1.8.7 ещё не
гонялся. Нужен полный OFF/ON расширения (менялись manifest + content.js), `scripts/sync-ext.sh`
уже выполнен.

## Заход 09-19 — обход шёл в ГЛУБИНУ, хвост ключевиков не ищется НИКОГДА

Тест-юзер прислал «No zero-touch greenhouse jobs to apply to yet». Разбор вывел на три вещи;
все числа ниже — замер живой базы 19.09, не прикидка.

**1. Симптом, с которого начали (гонка холодного старта).** `buildAtsQueue` дёргает
`POST /jobs/find-ats` и читает очередь СРАЗУ, а эндпоинт с #64 возвращается мгновенно и
собирает в фоновом потоке (~30 с). У нового юзера пул на первом Start ещё пуст → отказ с
советом «broaden your keywords», который винит юзера. Через 3 минуты в пуле было 160 строк,
из них 10 greenhouse проходят её поиск. **Не починено.**

**2. Корневой дефект — ширина обхода.** Ротация по ключевикам ЕСТЬ (`advanceKeyword`,
`content.js`), но идёт в глубину: `pagesPerKeyword = max(4, 24/n)`, Indeed листается
`start=` по 10. Кап платформы `MAX_PER_PLATFORM = 15` (`app/db/subscriptions.py:42`)
кончается внутри первого ключевика, а `kwIndex` сбрасывается в 0 на КАЖДОМ старте
(`background.js:1600`) — значит каждый прогон заново идёт с ключа №1.

Замер по `applications` (84 подачи):
- **Jedyn: 39 из 39 подач на keyword #1 («Welder»)**; «Fabrication», «Fitter» — 0, при
  221 Indeed-строке в его пуле.
- Igor: 21 из 45 на keyword #1; «health care» — 2.
- На 10 ключевиках это ровно 90% незатронутых профессий.

Довод, который решает: запрос идёт с **`sort=date`** (`content.js:3863`), поэтому страница N —
это постинги на N×10 позиций СТАРЕЕ. Страница 4 по «Welder» — залежавшиеся вакансии с сотней
откликов; страница 1 по «Fitter» — сегодняшние. Глубина тратит кап на устаревающий хвост
одного запроса, не увидев свежей головы остальных.
⚠️ Довод «Indeed ранжирует по релевантности» — НЕВЕРЕН, сортировку по дате просим мы сами.

**3. Что ОТВЕРГНУТО и почему** (чтобы следующая сессия не пришла к этому заново):
- **«Подавать auto из Indeed-пула по прямым ссылкам»** — нет. Замер 526 Indeed-строк:
  **96.6% без score** (508), **82% с пустым описанием** (430), **2/3 старше недели**.
  Ранжировать нечем, значит «лучшие из всех ключей» не существует; фит-гейту нужно полное
  описание, которое даёт только открытая страница вакансии. Живой поиск выигрывает по
  свежести и по полноте описания.
- **«Собирать Indeed на сервере, как ATS-борды»** — невозможно: живой тест
  `IndeedPlatform().scrape()` → **403 Forbidden**, и это зафиксировано намеренно
  (`SERVER_SCRAPE_SKIP`, `app/routers/jobs.py:48`). Живой поиск расширения И ЕСТЬ наш
  харвестер по Indeed/ZR — он шлёт увиденные карточки в `POST /jobs/ingest`. Оттуда все
  526 строк. Убрать живой поиск = остаться без инвентаря.
- **«Общий пул на всех юзеров»** — возможен ТОЛЬКО для ATS-бордов (публичные JSON API).
  Строки юзеров почти не пересекаются (**1.02x**, общих ссылок 1.7%) — экономии нет;
  пересекаются на 100% сами походы на 213 бордов.
