## Заход 09-11 (поздний вечер) — три дня нулей: режим подачи решал не тот, кто должен (#184)

**Сверка по БД, которую ждал прошлый заход: заявок нет с 09-08.** `applications` пуста за
последние 48 часов; последняя строка — 09-08 (ashby, 1 шт). При этом движок здоров: прогон
21:53–22:18 показал 0 строк «No job title» (фикс #174 подтверждён), обход открывал вакансии,
судья отвечал на каждую.

**Корень (#184, в проде): у одного решения было две власти.**

| | |
|---|---|
| профиль Игоря | `apply_mode = broad`, бар **35** |
| судья вернул | `fit_score 42` + `decision "skip"` — трижды |
| расширение гейтит | **только по `decision`** (`content.js:1632`) |
| результат | вакансии выше собственного бара пользователя пропущены |

Почему модель так отвечала: рубрика в промпте называет 35–54 «weak match», а стойка broad
говорит «применяйся широко». Модель разрешала это противоречие в свою сторону — и молча
переигрывала ручку, которую крутил человек.

Теперь решает бар режима (`score >= threshold`), слово модели осталось в ответе как
`model_decision` — телеметрия, не руль. Жёсткий блокер по-прежнему выражаем: промпт связывает
его со счётом 0–34, ниже любого бара. Fail-closed не тронут (нечитаемый счёт = 0 = skip,
неизвестный режим = standard, судья не поднялся = skip). `tests/test_fit_gate.py`, 13 кейсов.

**Следствие, которое надо увидеть глазами:** в broad заявки пойдут по совпадениям 35–54 —
ровно то, что режим обещает. Потолки на месте (`BROAD_DAILY_CAP=40/день` + кап тира). Если
первый живой прогон даст спам — вопрос не к гейту, а к ключевикам.

**Ключевики — вторая половина нуля, и она не баг.** У Игоря `["ai engineer", "project manager"]`
+ Майами. Выдача Indeed по «project manager» в Майами = стройка/кровля/HVAC, резюме —
маркетинг/диджитал. Судья скипал их ЧЕСТНО (5–30). Даже с починенным гейтом объём даст только
смена ключевиков на резюмешные. Решение за Игорем.

## Заход 09-09 (вечер) — гейт старта перестал угадывать (#171, ext 1.7.9)

Два гейта отказывали или запускали не тот режим на «улике», которую можно произвести, не имея
за ней ничего.

**1. Indeed.** `detectPlatformAuth` читал шапку `www.indeed.com`, видел `SignIn` и писал
`indeed=logged_out`. Indeed держит поисковый хост и хост подачи как РАЗНЫЕ сессионные
поверхности — эта шапка рисуется и для сессии, которая прекрасно подаёт. Запись читали **оба**
пре-флайта: `START_CAMPAIGN` в `background.js` и `QuickActions.startCampaign` на дашборде
(через `ping.js`, который берёт `platformConnections` из `chrome.storage` НАПРЯМУЮ, минуя
service worker — поэтому чинить надо было саму запись, а не два гейта по отдельности).

Правило теперь: **позитив доверяем везде** (меню аккаунта не отрисуется без сессии), **негатив —
только с доменов подачи** (`smartapply.indeed.com`, `secure.indeed.com`). Каждая запись несёт
`host`, на котором прочитана; `logged_out` без родословной (в т.ч. все старые записи — у них
поля просто нет) удаляется при чтении `getPlatformConnections()` и на `onInstalled`. Последнее
и расклеивает уже отравленные браузеры: без него дашбордный гейт продолжал бы отказывать и
никогда не дал бы service worker'у шанс прибраться.

Побочно: у логаута на www больше нет силы поставить обход на 2-часовую login-паузу — стенка
теперь ловится там, где она настоящая, с формой логина перед глазами.

**2. Auto vs Tap.** `background.js` брал `submit_mode` из `/campaign/status` под `catch {}`:
ответ не дошёл → `null` читался как `auto` → tap-юзер получал полный авто-walk по
несвайпнутому. У бэкенда та же дыра с другого конца — `get_submit_mode` глотал любое
исключение и отвечал `auto`.

`read_submit_mode()` теперь возвращает `None` вместо догадки (пустая строка профиля — это
ОТВЕТ `auto`, а не неизвестность), `/campaign/status` несёт `submit_mode_known`, расширение
отказывается стартовать с честным текстом. **Единого безопасного дефолта здесь нет**, и это
главное, что стоит унести: для подачи неизвестность обязана значить `tap` (заявку не отозвать),
для дневного капа — `auto` (у tap потолок выше, догадка подняла бы ban-safety рельс).
Кап-вызовы (`daily_limit`, readiness, stall-watch) остались на `get_submit_mode()`.

Проверено: 269 тестов зелёные (6 новых — `tests/test_submit_mode_unknown.py`), ruff чист,
`node --check` по всем JS. Ext синкнут в `~/Desktop/HireDrop-Ext`.

## Грабли захода (чтобы не наступать заново)

- Тест, зависящий от окружения (`.env` без/с ключами) — форсить состояние патчем (#143).
- Мок-тесты не ловят SDK-классы багов — денежный путь гонять РЕАЛЬНЫМИ SDK-объектами.
- `ruff format` на КАЖДЫЙ тронутый файл (провал #146 → красный main → #151).
- Ext-релоад программно: `HIREDROP_SET_FLAG hd_debug` → `HIREDROP_RELOAD_EXT` (мост
  ping.js), потом перезагрузить вкладки дашборда. UI-кнопки через osascript флачат —
  надёжнее postMessage тем же сообщением, что шлёт кнопка.
- Chrome-JS через AppleScript: `execute <tab> javascript "…"` (сафарёвское
  `execute javascript "…" in tab` даёт обманчивое `-1723 Access not allowed`).
  Настройка «Allow JavaScript from Apple Events» у Игоря включена давно — не просить.
- React-кнопки дашборда не всегда реагируют на `.click()` — слать
  pointerdown/mousedown/pointerup/mouseup/click.
- Порядок выката: сначала бэкенд в main (Railway), потом релоад ext — иначе новый вызов
  расширения бьёт в несуществующую ручку.
- Токен Игоря = cookie `sb-…-auth-token.0/.1` (base64- префикс → JSON.access_token)
  из его же вкладки; профиль писать через `POST /profile` ПОЛНЫМ телом (частичное
  затирает базовые поля дефолтами).
